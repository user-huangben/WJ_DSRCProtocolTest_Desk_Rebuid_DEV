# 北京地标协议测试用例迁移对照

## 1. 审计边界与结论

- 原程序入口为 `Wanji_Standard_DIALOG.cpp` 的第二个页签“北京地标协议测试”，实际显示 `m_dlgonechip`，其类型为 `CONECHIP_DIALOG`；因此本模块基线是 `ONECHIP_DIALOG.cpp/.h`，不是万集标准测试树中的单个“地标交易测试”。
- 原 C++ 工程只作只读行为参考；新实现仍位于独立 C#/.NET Framework 4.8 x86 上位机中。
- 原活动目录包含四个一级类别：OBU基本测试、OBU入网测试、OBU实验室检测、单片式OBU测试。
- 原统一调度器 `WJ_OneChip_TestRand` 实际只注册 A～X 共24个组入口。目录中写明“未实现”的项目，以及整个“单片式OBU测试”目录，均没有对应调度入口，不得在新程序中伪装为已实现。
- 当前阶段只完成目录、入口、公共参数和判定边界审计，并建立新窗体调度框架；每个真实协议处理器仍须在开始移植前继续展开其最终函数，逐帧完成三方对照。

## 2. 原程序公共执行框架

1. `CONECHIP_DIALOG::OnInitDialog` 建立测试树。
2. 开始测试时读取勾选叶子并编码为 A～X 调度字符序列。
3. `WJ_OneChip_TestRand` 按字符顺序取全局交易互斥量，检查停止标志，再创建对应测试线程。
4. 各组函数自行完成台发初始化、BST/VST、业务帧、结果判断和界面输出；原实现大量依赖全局状态。
5. 新上位机不复制全局线程和全局结构体，改为窗体统一队列、`CancellationToken`、共享 `DesktopCommService` 和后续专用服务类。

## 3. 已确认的公共配置来源

原 `CONECHIP_DIALOG::ReadIni` 明确读取：

| 配置项 | 原用途 | 新实现规则 |
|---|---|---|
| `[SET_Trade_GB]/number` | 交易类循环次数 | 对应交易用例使用，禁止套给非交易用例 |
| `[SET_Trade_GB]/interval` | 交易轮间隔 | 保留原单位，迁移具体函数时确认 |
| `[TRADE_SET]/19` | 0019交易参数 | 逐用例确认金额与出入口状态实际取值位置 |
| `[SET_Frame]/EF01` | ESAM系统信息 | 仅用于原函数实际读取该项的用例 |
| `[SET_Frame]/0015` | ICC 0015数据 | 仅用于发行/文件类对应流程 |
| `[SET_Trade_GB]/warn` | 原界面错误弹窗开关 | 新程序转为日志/结果，不在后台线程弹窗 |

其他次数、时序、路径、站点、BST模板和发行参数必须从各最终函数继续追溯，不能从上述公共项推断。

## 5. 子项清单中的特殊事实

- 指令集目录共有28项；原目录第11项和第12项名称均写成“取芯片序列号INS参数不正确”，必须以 `WJ_OneChip_instruction` 内部分支帧为准，不能按重复名称合并。
- 实验室 GetSecure 的4个子项没有描述名称，迁移前必须恢复其实际帧差异和判据。
- 实验室 TransferChannel：1～7项为同一读余额APDU重复1～7条；8～10项为ESAM取4字节随机数APDU重复1～3条；11项为IC通道混合读取余额、0015、0012；12项为ESAM通道进入3F00、读EF01、取芯片序列号。
- 原目录中的“未实现”不是测试失败。新框架将其标为不可执行审计项，不调用DLL、不生成伪造结果。

## 6. 每个真实用例接入前的强制检查表

1. 定位组函数内部对应子项分支及其调用的最终业务函数。
2. 记录台发初始化全部字段：BST间隔、重发间隔/次数、功率、信道、BID/UnixTime/LLC/MAC更新、超时。
3. 逐帧列出类型、完整字节、动态字段来源、长度、MACID、LLC和发送/接收方式。
4. 多APDU回复逐项解析长度、状态字和ReturnStatus。
5. 分开记录DLL请求成功、是否收到回复、APDU成功及整个用例通过。
6. 明确正常与异常路径是否发送单向EventReport，以及下一子项前等待。
7. 对文件、密钥、发行状态等持久修改给出实机风险提示和恢复策略。
8. 新旧帧与实机日志完成三方对照后，才把对应路径登记到北京窗体处理器映射。

## 7. 新上位机第二阶段框架映射

- `MainForm` 把同一 `DesktopCommService` 传给 `BeijingLocalStandardTestForm`，北京模块不自行打开串口或创建第二个DLL句柄。
- 窗体支持父子勾选、选中父级展开全部叶子、顺序调度、停止令牌、执行进度和测试信息显示。
- 用例通过“完整树路径 → 异步处理器”映射接入，避免使用原程序 A～X 字符和全局状态。
- 当前已登记“交易过程中响应广播帧”“交易过程中响应不同MAC”和“OBU基本测试 > 3、典型交易测试”；其他待迁移路径仍只报告目录状态，不调用设备。

## 8. OBU基本测试 > 3、典型交易测试

### 8.1 证据与迁移口径

- 原入口：`ONECHIP_DIALOG.cpp::WJ_OneChip_TestRand` 调度字符 `C`。
- 原最终函数：`TEST_ONECHIP_TRADE.cpp::WJ_OneChip_typicaltransfer`，固定执行 6 个分支；它不是万集备用测试项的 `WJ_Trade_typicaltransfer`。
- 金额取当前 `SetMe.ini [TRADE_SET]/19` 前 4 字节，出入口状态按原典型交易固定为 `04`；分支间隔取 `[SET_Trade_GB]/interval`。
- 原函数读取 `[SET_139_GBtransfer_num]/number`，但循环仍固定为 6，故新实现不把该配置解释为执行次数。
- 每个分支从当次 VST 重新取得 MACID、合同版本、发行方、合同序列号和 ICC0015；合同版本 `51/52` 使用 SM4，其余使用 3DES，避免沿用旧全局变量的前序状态。
- 新实现保留北京分支的 SetMMI 非强制判定：发送和记录实际请求/回复，但失败不单独否决分支。EventReport 始终是单向帧；正常结束要求发送成功，已取得 MACID 的失败路径也尝试发送一次清理。
- “校验车辆信息”由北京窗体复选框控制，默认勾选。勾选时按当次 VST 派生应用加密密钥，解密 GetSecure 车辆信息并与原固定 32 字节车辆数据比较。

### 8.2 六分支流程与判定

| 分支 | 帧流程 | 通过条件 |
| --- | --- | --- |
| 1 | BST/VST → GetSecure → 读0015 → 读0019 → 读余额 → 读0019+余额 → 读0015+余额 → 读0015+0019+余额 → 消费初始化 → 更新0019 → 扣费 → SetMMI → EventReport | 所有必选帧 DLL 请求/响应成功；TransferChannel 每条 APDU 为 `90 00` 且 ReturnStatus 为 `00`；可选车辆信息一致；EventReport 发送成功 |
| 2 | BST/VST → GetSecure → 消费初始化 → 更新0019+扣费 → SetMMI → EventReport | 同上 |
| 3 | BST/VST → GetSecure → 读0015+0019+余额 → 读0019+EF08 → 消费初始化+更新0019 → 扣费+读余额 → 取8/16字节随机数 → 外部认证+更新EF08 → SetMMI → EventReport | 从当次 VST/读卡回复取得版本及分散因子；随机数长度符合算法；复合回复中每条 APDU 均成功 |
| 4 | BST/VST → GetSecure → 读0019+余额 → 消费初始化 → 取交易认证 → SetMMI → EventReport | 交易认证参数从当次消费初始化回复提取，不使用旧全局残留 |
| 5 | BST/VST → GetSecure → 读0019+余额 → 消费初始化+更新0019 → 扣费+读余额 → SetMMI → EventReport | 所有复合 APDU 和 ReturnStatus 成功 |
| 6 | 与分支4相同 | 与分支4相同 |

### 8.3 与原程序的已确认差异

1. 原程序只在分支1建立部分算法/分散上下文，后续分支可能沿用全局值；新实现每个分支独立解析当次 VST。
2. 原分支3先读取 VST 字段、后判断 `fVST` 返回值；新实现先确认 DLL 成功和长度，再解析字段。
3. 原分支4/6使用全局 `num_tuoji`；新实现从当次消费初始化回复提取交易认证参数。
4. 原失败路径可能直接跳出而不发送 EventReport；新实现取得 MACID 后尽力执行单向断链清理。
5. 原 EventReport 返回值不参与最终判定；新实现要求正常结束时发送成功。
6. 原 Release 包未提供 `OBU基本测试_典型交易测试` 实机日志，本节依据旧源码静态审计；真实扣费、0019/EF08写入、蜂鸣和六分支最终通过仍需实机确认。
